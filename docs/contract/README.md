## Using the Postman collection

1. Import `postman_collection.json` into Postman.
2. Set collection variables: `base_url` (dev: `http://localhost:7373`),
   `api_key` (a tenant API key).
3. Run the **Setup** folder first — login/register/refresh and platform
   login requests capture tokens into collection variables automatically
   (`access_token`, `refresh_token`, `super_admin_token`).
4. Headers are pre-wired to the runtime truth: tenant routes carry
   `x-api-key` (+ Bearer where required), `/admin/*` routes carry both,
   `/super-admin/*` routes carry only the platform Bearer token, and
   public routes (`/auth/login`, `/webhook/finecore`, `/tenants/onboard`,
   `/admin/team/invite/accept`, health) carry none.

## Notes

- The OpenAPI document reflects the AJV schemas. Two known gaps between
  schema-level `security` and middleware reality are encoded in the
  Postman generator (not the OpenAPI doc): `/admin/*` also requires the
  tenant API key, and `/auth/*` routes are not public. A future pass could
  align the schemas; the runtime behavior is the authority.
- Super-admin impersonation returns the tenant's API key + OWNER token —
  see `platform-admin-prompt.md` for the safe handoff pattern.
